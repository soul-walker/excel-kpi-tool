评审说明与速览

这份文档是什么：我把参考仓库 school-kpi 的 Go 代码、示例 Excel 数据、以及旧 Tauri 客户端全部读了一遍 （核心文件：cmd/*、collect/**、generate/bukeshi.go、kpi_generate/kpi.go、example_data/*.xlsx）， 在此基础上给出通用化工具的目标架构与实现思路。文档是可交互的：你可以展开细节、切换技术选型、逐节评分并勾选问题， 最后在评审操作台一键导出你的结论，把文本贴回对话即可。
TL;DR（一句话版）
  • 通用化的本质不是"做一个万能计算器"，而是把老代码里的三类硬编码拆成一份可保存、可编辑、可校验的"方案（Scheme）"配置：读什么（文件/表/列如何解析）、怎么算（参数、聚合、逐行公式、分组覆盖）、写哪里（回写模板的哪些列 / 生成新表）。
  • 计算语义全部来自老代码：人员名称为 key 的记录聚合 + 按"非校聘/校聘"两组公式求值 + 原地回写已排好版的模板（如 绩效.xlsx）。这套语义可以 1:1 表达为配置。
  • 最大的技术风险不是"算"，而是"回写"：要求打开老师做好的 Excel 模板、只改动指定列、保留原有格式/其他工作表。按你的评审，读写层选定 Rust + umya-spreadsheet（支持原格式回写），因此 M0 的第一个 Spike 就是验证它对真实模板（含 WPS 产物）的保格式写回。
本轮评审已定的技术栈（2026-09-05）：D1=Godot 做 GUI · D2=全 Rust，xlsx 读写用 umya-spreadsheet · D3=轻量 DSL · D4=JSON+版本迁移 · D5=以本仓库为根重构。详见第五节决策台。
同日补充的三项决策：① 参数统一内嵌方案文件，不再从 配置.xlsx 读取（此前用 xlsx 是因旧客户端无存储，现方案文件即存储）； ② 核心逻辑保留 Bevy ECS 实现架构，不移除 godot-bevy；③ 方案以 JSON 文件存储（不引入 SQLite），评估见3.7 节。
Q1~Q4 全部已答（2026-09-05）：
  1. Q1（使用者）：老师自己跑 → GUI 默认"月度运行向导"（选数据目录→选方案→校验→预览→运行），高级方案配置为单独编辑模式（见第四节）。
  2. Q2（身份）：先姓名 + 报重名 → 见 A4；工号/人员主档等作 M4 演进项。
  3. Q3（回写）：A/B 可切换（apply: inplace | copy），面向老师的主流程默认 A（写回原文件 + 自动 .bak）；详见 3.8 节。
  4. Q4（公式）：不会演进到 Excel 完整语法 → DSL 无需兼容预留，函数库可扩展即可（已并入 D3 说明）。

1.3 老代码中真实存在的"计算语义细节"（对拍基线，做通用引擎时不可漏）

以下细节全部从 kpi_generate/kpi.go、collect/collect.go 逐行还原，作为"通用引擎必须能表达这些"的验收样例。

  • 门控 Gate：请假超过 N 天（配置.请假超过天数，统计非"公"假的累计天数）后，该人几乎所有项置 0 或留空。
  • 字段取值规则分三种：缺纪录→0（如课时、岗位奖）；缺纪录→留空（如补课时、早读≤0、扣课时合计0）；命中且>0→写值、否则空（早读/班主任/折扣等）。空与 0 的差异会体现在最终 Excel 单元格上，必须建模。
  • 公式链（非校聘列）：课时S = 课时.总计（门控下为0）；课时X = max(0, 课时S−基础课时)；课时费S = 课时S×课时费；课时费X = 课时X×超课时费；课时周费 = 课时费S+课时费X；课时月费 = 周费×4；考勤奖 = 参数值；岗位奖/教研组长/年级组长/行政后勤/行后 = 岗位表值；扣课时 = −Σ(课时周费÷5 × 请假天数)，仅统计 类型∉{婚,公,丧,产} 且该假有替课 的记录；请假 = −min(100, 事假天数×事假单价 + 病假天数×病假单价)；补课时 = 补课时表费用；未参加升旗、集会 = 台账值；早读 = 台账小计；班主任 = 班主任表应发。
  • 折扣：{教研组长,年级组长,行政后勤,班主任}中 >0 的数量 ≥2 时取其中……（代码里 min() 的实现是"取最后一个非零值"，见风险清单 R3）
  • 合计1 = 课时月费 + 考勤奖 + 岗位奖 + 扣课时 + 补课时 + 请假 + 未参加 + 早读 − 折扣（负项带负号求和）；合计2 = (班主任+教研组长+年级组长+行政后勤+行、后) ×（非校聘 0.4 / 校聘 1）；合计 = 合计1+合计2。
  • 非校聘另有：上浮30% = 合计×1.3；实际发放 = round(上浮30%)。校聘实际发放 = round(合计)。个税/取整/无格式列模板里存在但代码未算（预留列）。
  • 表头差异：非校聘 28 列、校聘 26 列（少"上浮30% 取整 无格式"中的两列，以模板为准），两 sheet 的表头集合不同 → 校验规则也不同。
  • 行定位假设脆弱：写入行号用的是 GetRows 返回切片下标+1；一旦模板中出现被 Excel 压缩掉的空行或插入行，位置就会错位。示例模板带"标题行/合并单元格/自动筛选（A2:AD80）"，能跑通属于侥幸。
  • 补课时派生：费用 = 节数 × 7（硬编码常量）；补课时.xlsx 生成后又被绩效流程当输入读取——是"先跑 bukeshi 再跑 kpi"的原因，正确建模应是方案内的依赖图。

1.5 痛点归纳（为什么要通用化）

① 改规则 = 改代码
调一个系数、加一种扣款、改列位置都要动 Go 源码、重新编译、全校换 exe。
② 用姓名当主键
去空格/换行是唯一归一化；重名、别名、台账与模板姓名不一致时静默算错或找不到人。
③ 输入输出耦合模板
列名匹配靠硬编码字符串，模板一旦改版（增列/改列名/插空行）立即 panic，或静默写错行。
④ 流程时序靠人
先补课时后绩效、产物又作输入，顺序错了结果就错；中间产物与模板混在同一目录，无版本、无审计。
⑤ 错误体验差
缺列/坏数据直接 panic + exit 1，日志在 stderr；用户无法知道"哪一行哪一列错"。无 dry-run、无预览。
⑥ 配置也是 Excel
参数在 配置.xlsx 里手工改，没有结构校验、历史版本与"这次改了哪些参数"的追溯。

二、需求与"通用"边界

2.1 目标定义

做一个配置驱动、带 GUI 的 Excel 台账计算工具：用户用界面把四件事描述出来—— (1) 读哪些记录文件、列怎么解析；(2) 有哪些参数/常量；(3) 计算公式（含按分组覆盖）；(4) 结果写回哪个文件的哪些列（或生成新文件）—— 保存为一份可复用的"方案(Scheme)"，之后每月换数据一键重跑。规则演进不再动代码，只改方案。

2.2 "通用"的三层边界（建议）

层级由用户配置（GUI）由工具内置（代码）
数据接入层文件/目录/多文件、sheet、表头行号、列→字段映射、列类型、空值/向下填充/续主记录、忽略行、姓名归一化、人员过滤 xlsx/csv 解析引擎、合并单元格读取、类型转换、分块读取（大文件）、编码
计算层参数表、派生明细、聚合指标（按人/按组求和计数等）、逐字段公式、分组（如 非校聘/校聘）公式覆盖、全局门控条件 表达式解释器 + 内置函数库（Excel 风格子集）、依赖拓扑排序、类型/引用检查、循环引用报错
输出层目标模板文件 + sheet（可随分组切换）、按表头名/列号定位写列、数字格式、空值行为（留空/0/公式）、新建文件模板、人员行匹配策略（按 key 定位行 / 追加行） xlsx 原地回写保格式、新文件生成、样式应用、覆盖前备份、差异报告
建议的"不做"清单（MVP 边界）：不追求任意编程语言式规则；不内置完整 Excel 公式引擎（见 D3）； 不做多人协作/权限系统（单机）；不把"任意复杂 Excel 版式"都当输入（复杂版式仍建议先整理成规整台账）。 这些以"扩展点"预留：公式函数库可加、解析器支持插件、方案文件版本化可迁移。

三、目标架构与核心模型

3.1 总体架构

核心原则：引擎（headless，可测可复用）与界面（GUI）分离；引擎吃"方案配置 + 输入文件集"， 输出"结果工作簿/差异报告/问题清单"。GUI 只是方案的编辑器和运行面板。

3.2 核心领域模型（一份"方案"由什么组成）

概念说明对应老代码
Scheme（方案）带 schemaVersion 的完整配置（JSON），含下述所有对象；GUI 编辑、保存、导入导出。cmd 下的一套固定逻辑
Source（数据源）文件（或目录通配）+ sheet + 表头行号 + 起始行 + 列定义 + 行过滤 + 归一化 + 解析技巧（填充/续主）每个 collect/xxx 的 fileName/sheetName + readRows
ColumnDef（列定义）定位方式(按表头名/列号)、类型(文本/整数/小数/金额/布尔/日期)、别名、可为空、主键列标记常量表头名 + strconv 解析
Parameter（参数）标量参数集合（规则常量）；随方案文件存储与版本化；政策调整时 GUI 编辑并另存新版本，不按月复制KpiConfig（原 配置.xlsx → 现并入方案文件）
Entity 主维度计算对象：key 字段（姓名/复合键）、归一化、重名策略；每个数据源/派生表都隐含 keymap[姓名]
Transform（派生）由源数据派生新明细：过滤→字段重映射→聚合(按 key group)→新表（仍带 key）。例：请假替课行→按替课老师汇总节数/费用generate.collectTiShangKe
Aggregate（聚合指标）对某明细按 key 求 sum/count/avg/max/min/last/条件计数（如"非公假累计天数"）collect.go 里的 Get/Cal 系列
ComputeGroup（计算分组）一组共享计算字段上下文 + 覆盖；如"非校聘/校聘"。分组条件=输出 sheet 或人员属性列calAndWriteJx(xp=false/true)
CalcField（计算字段）name + 表达式 + 类型 + 依赖；表达式引用：数据源字段、聚合指标、参数、其他字段kpi.go 里每个 writeCell 前的公式
Output（输出）两种模式：patch 模板（文件+sheet 随分组、行定位=按 key 匹配行、字段→列(表头名/列号)、数字格式、空行为）；生成新文件（表头模板、来源明细/计算表）kpi_generate / generate.bukeshi
校验规则问题级别：error/warn/info（缺 key、重名、列缺失、类型错、数值异常、缺人名单）panic + slog

3.3 运行模型：编译期 / 运行期

① Compile（点"保存/校验"时，秒级）
  • 解析方案 JSON → schema 校验 → 构建对象模型；
  • 静态检查：表达式引用字段存在、类型可推断、无循环依赖、公式函数存在、输出列能在目标模板表头中找到；
  • 打开每个输入文件，读取表头行做 实际列对齐（名字匹配/列号回退），列出"与方案预期不符"的警告；
  • 产出可执行 DAG（源→派生→聚合→计算→输出）与错误清单。编译不通过就不允许运行。
② Execute（点"运行"时）
  • 依 DAG 顺序执行；数据行问题不中断整体，落入问题清单（带文件名/sheet/行号/原因）；
  • 写前可选 dry-run：在内存中算出每人每字段，GUI 网格预览 + 与当前模板值 diff；
  • 写后输出：备份原文件 → 写回；记录审计日志（方案版本、参数快照、运行时间、人数、警告数）。

3.6 Rust 技术栈下的 xlsx 读写设计（umya-spreadsheet）

  • 读取：umya-spreadsheet 读取工作簿到内存对象；解析层把"表头行 + 列映射 + 填充/续主 + 类型转换"抽象成通用 TabularReader，引擎只面对规整的行/列对象，不直接摸 XML。
  • 模板回写：用 umya 打开目标模板 → 定位行/列 → 只改目标单元格值（set_sheet_value），保留样式、合并单元格、列宽、其他 sheet；保存时建议默认另存副本，原文件自动备份。
  • 隔离层：引擎内部定义薄 trait（如 WorkbookIO: read_table / open_template / write_cell / save），umya 只作为其中一个实现。若某天遇到 umya 对特定 WPS 产物兼容不佳，可替换或补一个"worksheet XML 最小 patch"实现，不牵动上层。
  • 新表生成（补课时.xlsx 等）：仍走 umya 新建工作簿 + 表头/样式写入，同一 trait。
  • 验证门：M0 Spike 必须用真实模板（Excel 与 WPS 各一份产物）验证"写回后：样式逐格一致、无 repair 提示、公式缓存与合并单元格不受影响"，并落成自动化回归用例。

3.7 方案的存储形态：JSON 文件 vs SQLite（评估结论：方案本体用文件，不用 SQLite）

要回答"GUI 配好的方案如何记录"，先把要持久化的内容分成两类：① 方案本体（数据源映射、参数、公式、分组、输出定义、schemaVersion）——它需要被 diff、评审、复制、跨月复用；② 运行痕迹（某次运行的文件集、参数快照、结果、问题清单）——它是日志性数据。

维度方案 = 单个 JSON 文件方案存 SQLite
人读 / 评审 / diff优：git、编辑器可直接看差异；方案即"可评审产物"差：二进制库，需导出才能看
导入 / 导出 / 分享 / 备份直接复制一个文件库文件整体拷或用 API 导出，麻烦
三端一致读取（Godot / CLI / 回归测试）serde 反序列化，零额外依赖每端都引入 rusqlite/sqlx，接入面大
版本升级 / 迁移schemaVersion + 迁移函数（与 D4 一致）还要维护 schema_migrations 表
按月的运行复用方案跨月不变，仅把运行目录绑定到本月数据目录方案仍不变，SQLite 无额外收益
损坏排查 / 应急修复文本可直接审查、手工改回需要 SQL 工具，普通用户无法自查
多用户并发写不支持（单机单人场景可接受）理论上支持，但本项目不需要
运行历史 / 审计（若做）另写结构化日志（jsonl/csv）即可天然适合，但属于 M4 可选项
结论：方案本体用单个 JSON 文件，不引入 SQLite。理由：方案是跨月稳定的规则集（每个月的差异只在数据目录），其价值在于可读、可 diff、可版本管理、可复制（复制后作为新学校/新规则集的基础）；文件形式与 D4/版本迁移一致，且 Godot、CLI、测试三端读取成本最低。
运行痕迹：MVP 先写结构化日志（每行一条 JSON：时间/方案哈希/输入文件指纹/结果汇总/问题清单）；若 M4 有"历史查询/趋势对比/审计报表"诉求，再引入本地 SQLite 存运行历史，不存方案本体。
落地约定（已修正）：方案是跨月稳定复用的"规则集"，不按月复制。一个方案（如 schemes/高中月绩效.json）定义一套数据源映射/参数/公式/分组/输出，可跨月反复使用； 每个月的差异只在于本月台账所在目录：运行台让老师"选择本月数据目录"（沿袭旧程序 -d 工作目录 的习惯），引擎把该目录绑定到占位符（如 {monthDir}/课时.xlsx）来解析输入，输出默认也写到该目录。 参数作为规则常量内嵌方案：仅在政策调整（如学期/年度改课时费、考勤奖）时在 GUI 中改值并另存为新版本（保留历史可 diff），而不是每月复制一份方案。

3.8 回写在担心什么：三种输出模式的说明（Q3 决策材料）

先说结论："回写模板"这件事本身在老程序里已被 Excelize 验证可行——担心点不是"能不能写"，而是下面四类保真与安全问题：

  1. 格式保真：模板是老师精心排的版（标题合并、行高列宽、边框底纹、数字格式、自动筛选、冻结窗格，甚至批注/图片/条件格式）。任何写库都要把整份文件重新打包；若库对某一项不忠实，就会"数字对了、表变样了"。逐格肉眼核对几百人×30 列不现实，所以 M0 要自动化"视觉等价"检查（对比改写前后 XML/样式表 + 抽样人工打开确认）。
  2. 公式与缓存：模板若某些格是 Excel 公式（不是我们写入的值），写库可能破坏公式或缓存值，导致打开提示"修复/重算"或显示旧值。回写层应"只改目标单元格的值，其余一律不动"。
  3. WPS 产物兼容：学校文件很多由 WPS 保存，XML 可能有非标准痕迹。Go 的 excelize 对这些老文件已被验证；Rust 的 umya 需要用同一批真实文件做 Spike 验证，不过则落 3.6 的 XML 最小 patch 备胎。
  4. 原文件安全：直接覆盖老师交来的文件，一旦写坏（崩溃/库 bug），唯一原件就没了 → 必须自动 .bak 备份，或另存为新结果文件。

因此"回写"不是二选一，而是方案输出上的一种策略字段：

模式行为优点代价/风险
A · 写回原文件（原地补丁）打开老师当月模板 → 只改目标列 → 保存回原路径（先自动写 .bak）与旧程序一致，老师按原文件名提交，习惯不变原文件被改；靠 .bak + 运行前 diff 预览兜底
B · 另存结果副本生成"绩效-2026-09-已算.xlsx"，原文件永不动原文件零风险；可逐格与原文件对比提交/命名多一步；需记住使用新文件
C · 内置模板生成不依赖当月模板版式，按内置样式模板从零画新表版式完全可控工具要维护版式定义；老师自行改版式时难以跟随；仅适合"从零产物"（如补课时.xlsx）
已定（2026-09-05）：每个输出可配置 apply: inplace | copy，面向老师的主流程默认 A（写回原文件，先自动 .bak），并保留 B（先核对再定稿）供切换；C（内置模板生成）仅用于"生成新文件"型输出。无论 A/B，写库保真要求相同，M0 的视觉等价验收门都必须过。
Q3 选择（已定：A/B 可切换，默认 A）

四、GUI 交互设计草案

GUI 的目标用户是"会 Excel、不懂代码"的老师。原则：每个步骤都有所见即所得的表格预览；错误直接指向"文件/表/行/列"；把复杂解析藏进向导。

按 Q1（老师自己跑）拆成两个界面档位：默认打开的是"月度运行向导"（选本月台账目录 → 选方案（如 高中月绩效）→ 一键校验 → dry-run 预览 → 运行 → 结果/问题清单），老师每月只用这一个界面； "方案配置"作为单独编辑模式（工具栏/菜单进入），用于新建/复制方案、改数据源映射、公式、参数与输出设置。普通老师不配置，只看运行向导的结果是否与自己的表一致。

七、风险与未决问题

R1 · 模板回写保格式（最大技术风险，已定用 umya-spreadsheet 验证）

定稿采用 Rust + umya-spreadsheet 做读与"原格式回写"。umya 对复杂模板（WPS 产物、合并单元格、筛选、公式缓存）的兼容性必须用真实文件验证，不能只信文档或宣传。

  • 缓解 1：引擎内定义 WorkbookIO trait 隔离 umya，必要时可局部换实现（calamine 读 + 自研 worksheet XML 最小 patch 写）而不动上层；
  • 缓解 2：M0 Spike 验收 = 对 school 真实模板写入后逐格 diff + Excel/WPS 打开无 repair 提示，并固化为自动化回归；
  • 缓解 3：回写默认另存副本，原文件保留备份，降低损坏风险。
R2 · 数据质量：姓名 join 的可靠性与重名

老代码只做去空白/换行。通用化后至少要：归一化规则可视化、join 缺失/重名/一人多值上报问题清单； 长稳方案是"教研组+姓名"复合键或引入人员主档（老模板本身有"教研组"列可作分组维度）。

R3 · 老代码中疑似 Bug / 需对拍确认的语义
  • collect.go 的 min() 名为取最小、实为"取最后一个非零值"（用于折扣档位判断），需与你的真实意图确认并写进回归用例；
  • 扣课时 = 课时周费/5 × 天数，仅对"有替课且类型∉{婚公丧产}"的假；请确认"婚/丧/产假"是否真的不扣；
  • 请假扣款封顶 100 的规则、事假与病假是否叠加后封顶（代码是总额>100 则取 100）；
  • 示例 配置.xlsx 缺"是否对课时月费进行折扣"项、领导绩效.xlsx 有采集代码但未被主流程调用——确认是否为废弃流程。

建议在 M1 之前由你逐条确认，并把这些做成对拍用例，避免"复刻了一个 bug 还自洽"。

R4 · 版本与追溯：参数随方案后如何审计

参数已内嵌方案文件（规则常量）。建议：方案带 schemaVersion + 编辑版本号；每次运行在日志中记录方案文件哈希 + 输入文件指纹 + 逐人结果摘要；GUI 提供"与历史版本对比"（参数/公式差异高亮），避免"某人为何少了 X"无法追溯。

R6 · Godot 做"编辑器型 UI"的开发成本（已定 D1 后的主要工作量风险）
