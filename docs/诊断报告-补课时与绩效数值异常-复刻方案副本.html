诊断报告：补课时输出 / 绩效回写数值不对

日期：2026-09-08　·　问题对象：Godot 用户方案副本（user://schemes/高中月绩效复刻.json）在 2023-09 数据上的运行结果
一句话结论：引擎与上次修复均无问题（本次输出已全部是正常数值、不再是乱码）。问题出在你运行的这份方案副本被改过，与仓库里对拍 golden 的「高中月绩效复刻」已不一致，改动造成了 4 类数值偏差；补课时第一个姓名空白则暴露了一个引擎空单元格比较语义与方案写法的既有隐患。
  • ① 补课时/绩效“补课时”列错：派生 bukesh 被改成按「请假天数」求和、费率用「课时费 1.5」而不是旧口径「替课节数 × 补课时费 7」；参数「补课时费」被删。
  • ② 补课时第一行姓名空白：没有替课的请假行没被过滤掉，被聚合到「姓名=空」的一行里（7 天 / 10.5 元）。
  • ③ 绩效“请假”列普遍偏低/消失：请假扣款金额聚合里引用了排在它后面的两个聚合（请事假/请病假天数），引擎按声明顺序计算且只能引用前序聚合 → 全员扣款金额=0。
  • ④ 大量小数点后微小差异：课时源列丢了 bits:32，未复刻旧程序 ParseFloat(s,32) 的四舍五入。

对照基线 = 旧程序 golden（2023-09-golden/）。用户方案副本位于 C:\Users\walker\AppData\Roaming\Godot\app_userdata\kpi_tool\schemes\高中月绩效复刻.json；仓库 schemes/高中月绩效复刻.json 未改动、仍是正确基线。

3. 根因逐条分析

3.1 派生 bukesh 口径被改写 → 补课时.xlsx 与绩效「补课时」列全错

方案副本里 derived.bukesh（以及新文件输出、绩效字段）被改成：

# 仓库基线（=旧程序 golden）：
bukesh 列：姓名=GROUP_BY(替上课老师)  节数=SUM(节数)  费用=节数 × 参数.补课时费(7)
绩效「补课时」字段 = bukesh.费用
补课时.xlsx 输出列 = 姓名 / 节数 / 费用

# 你的方案副本（当前）：
bukesh 列：姓名=group_by(替上课老师)  天数=sum(天数)  课时费=天数 × 参数.课时费(1.5)
绩效「补课时」字段 = bukesh.课时费
补课时.xlsx 输出列 = 姓名 / 天数 / 课时费（sheet 名也改成 替上课课时）
  • 把「替课老师实际代了几节课（节数）」错算成了「请假人请了几天假（天数）」，且费率用错参数（1.5 vs 7，参数「补课时费」也被删除）。
  • 例：向浩波替吕红冰 24 节 → 应 24×7=168；你的方案算成吕红冰的请假 10 天×1.5=15。
  • 例：李少波替袁萍 2 节 → 应 14；因“天数”只写在请假记录首行（王艳那行），李少波行的天数空白 → SUM=0。
  • 若本意确要输出旧格式（学校历来用 节数×补课时费），应把 bukesh、字段与 new_file 列全部改回基线；如另有新口径请先定口径再改。

3.2 补课时第一行姓名空白：空单元格没被 where 过滤掉

bukesh 的过滤条件写成 请假表.替上课老师 != ''。引擎里“空单元格”是 Empty，而 Empty != '' 为真（空值 ≠ 空字符串），所以没安排替课的请假行（该格是空白）全部漏了进来，被 GROUP_BY(替上课老师) 聚成“姓名=空”的一行：7 天 / 10.5 元。

引擎的正确写法要先把空值并成空串：

(请假表.替上课老师 ?? '') != ''   // 或单问号：请假表.替上课老师 ? ''
既有隐患说明：仓库基线里 bukesh 的 where 同样没加 ?? ''——以前 bukesh 只被绩效字段“按姓名查值”使用，这行空名数据永远不会被查到，所以测试全绿。一旦像你现在这样把 bukesh 落成新文件，空名首行就会暴露出来。补课时输出要落地，无论用哪套口径都建议先补 ?? ''。

3.3 绩效「请假」列普遍消失：聚合声明顺序被 GUI 打乱

你的副本里聚合定义顺序为：请假超总天数 → 请假超额 → 请假扣款金额 → 扣课天数 → 请事假天数 → 请病假天数。

引擎 compute_aggregates 按声明顺序逐条计算，聚合.xxx 只能引用已经算好的前序聚合。因此「请假扣款金额」计算时，排在它后面的「请事假天数/请病假天数」还不存在 → 引用落空 → 结果全是 0：

实测（引擎内部，方案副本）：
  请假扣款金额 / 薛国庆 = 0.0     （其请事假天数=1，1×20 应=20）
  请假扣款金额 / 阎秦安 = 0.0     （其请病假天数=2，2×10 应=20）
  → 绩效「请假」列对所有人都是空；仓库基线里 请事假/请病假 定义在 请假扣款金额 之前
  • 仓库基线顺序：请假超总天数 → 请假事假 → 请假病假 → 请假扣款金额 → 请假超额 → 扣课天数。
  • 这条同时是「引擎健壮性」问题：对声明顺序这么敏感、且前向引用会静默得 0 而不是报错，值得后续给引擎加“聚合依赖拓扑排序”或校验告警（见第 5 节建议）。

3.4 扣课天数与「空值比较」叠加错位

副本里「扣课天数」聚合被改为直接对请假表物理行求和（where 也无 ?? ''），而不是仓库基线用的 qingjia_jl「记录视图 + (替上课老师 ?? '') != ''」。

  • 没安排替课的病/事假也被计入扣课天数（空值漏过滤）；仓库基线靠记录视图 + ?? '' 排除。
  • 例：薛国庆（事假 1 天、无替课）→ 副本算得扣课天数=1 → 绩效“扣课时”被写成 -5.2，golden 应为空。
  • 同时副本方案里保留了一份 qingjia_jl 数据源，但没有任何聚合/派生引用它（成为死配置），进一步说明这份方案是手工改乱的半成品。

3.5 课时源列丢 bits:32 → 大量尾差

旧程序用 ParseFloat(s,32) 读“总计(课时)”列，仓库基线在 keshi.课时 上标了 bits:32 复刻该行为。你的副本里该列的 bits 被删了 → 有课时的老师整条链（课时S→课时费→课时周费/月费→合计→上浮/实发）都出现第 6~7 位小数差异：

李纯福：11.4        vs golden 11.399999618530273
解凌云：33.6        vs golden 33.599998474121094
校聘 141 处差异里绝大多数属于这一类

这类差异肉眼几乎看不出来，但对拍（数值精确相等）会失败；若交付只以对拍为准则，需要补回 bits:32。

5. 修复建议（待你拍板）

建议 A（必做）｜把方案副本对齐回“对拍基线”口径

  1. bukesh：列改回 姓名=GROUP_BY(请假表.替上课老师)、节数=SUM(请假表.节数)、费用=节数×参数.补课时费；重新加回参数「补课时费=7」。
  2. bukesh 与「扣课天数」的 where 都写成 (…替上课老师 ?? '') != ''（空值先并空串）。
  3. new_file「补课时」输出列改回 姓名/节数/费用，sheet 名按需取 替上课补课时（golden 命名）。
  4. 恢复聚合声明顺序：请事假天数、请病假天数 在 请假扣款金额 之前。
  5. keshi.课时 恢复 bits:32（如需与旧程序逐格一致）。
  6. 扣课天数改回引用 qingjia_jl 记录视图；不用的 qingjia_jl 源若保留请说明用途。

建议 B（引擎加固，可选）

  1. compute_aggregates 增加拓扑排序：聚合引用 聚合.x 时若 x 尚未计算，自动重排或报“循环/前向引用”错误，杜绝“静默 0”。
  2. validate 对聚合“引用未定义/前序未定义”给 error（现在这种引用跑起来静默错最危险）。
  3. 对“空单元格 ≠ 空串”的 where 比较给出警示或在文档标注（方案侧统一 ?? '' 即可）。
