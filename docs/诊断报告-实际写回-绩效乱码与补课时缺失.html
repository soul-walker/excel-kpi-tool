诊断报告：高中月绩效复刻 · 实际写回后「无补课时表 + 绩效表乱码」

日期：2026-09-08　·　工作目录：excel-kpi-tool　·　Git HEAD：c225ad0　·　数据月份：testdata/2023-09
一句话结论：两个现象是两个相互独立的缺陷，都发生在「写回」环节：
  • ① 不生成 补课时.xlsx —— 你选的方案 schemes/高中月绩效复刻.json 的 outputs 里只写了 1 个输出（回写 绩效.xlsx），从未包含「把派生表 bukesh 写成 补课时.xlsx 的 new_file 输出」。运行器忠实地只做了方案里声明的那一件事。旧的样例方案 高中月绩效.scheme.json 是含两个输出的，复刻方案在做表达式迁移时把它漏掉了。
  • ② 绩效表出现一串名字 —— 你把绩效表数据区清空后保存时，表格软件（该文件元数据显示是 腾讯 Office / Tencent office）把目标单元格全部写成了 t="s"（共享字符串型）的空单元格；引擎的「最小 XML patch」写值时只替换 <v> 文本、不会改单元格的 t 类型，于是把数字 100 等写进了字符串型单元格。Excel 一族会把 <v>100</v> 当作「共享字符串表第 100 项」去显示——正好是老师的姓名（如「肖雅静」）。计算本身是对的，是单元格类型被写坏。

3. 根因①：方案缺「补课时」new_file 输出

3.1 现象层面的解释

运行器 runner::run_scheme_outputs 的行为是：方案里声明了几个输出，就跑几个（遍历 scheme.outputs）。你选的方案 JSON 里 outputs 只有 1 个：

schemes/高中月绩效复刻.json → outputs 数组仅一项：
  [0] id="jx"，kind="patch_template"，file="绩效.xlsx"（回写 非校聘/校聘 两个 sheet）

所以点「实际写回」只会写 绩效.xlsx，不可能凭空生成 补课时.xlsx。

3.2 方案文件为什么缺这一项（溯源）

  • M0 样例方案 schemes/高中月绩效.scheme.json 里是有两个输出的：jx（回写绩效）+ bks（new_file，把派生表 bukei 写成 补课时.xlsx）。
  • M1 的复刻方案 高中月绩效复刻.json 在把表达式迁移为块语法时，只保留了计算需要的派生视图 bukesh（供绩效表里的「补课时」列引用 bukesh.费用），忘了把对应的 new_file 输出一并带过来——从该文件最早一次提交（c126902）起就一直是单输出，属于漏项而非本次运行引入。
  • 引擎本身完全支持这种输出，证据：runner.rs 单测 run_outputs_inplace_backup_and_match_golden 和 exec.rs 单测 bukeshi_new_file_matches_golden 里，都在运行前手动往方案内存对象里追加一个 new_file 输出：
// engine/src/runner.rs（单测，注释原文）
// 追加一个 new_file 输出（补课时新表），走同一个运行入口。
v.scheme.outputs.push(OutputSpec {
    id: "补课时新表".into(),
    kind: OutputKind::NewFile(NewFileOutput {
        file: "{monthDir}/补课时.xlsx".into(),
        from: "bukesh".into(),
        sheet: "替上课补课时".into(),
        columns: vec![ 姓名, 节数, 费用 ],
    }),
});

也就是「测试代码帮方案补上了它本该自带的那一项」——方案文件缺输出这件事，仓库里早有痕迹。

修复动作 A：在 高中月绩效复刻.json 的 outputs 里追加第二个输出（new_file：bukesh → 补课时.xlsx，sheet 替上课补课时，列 姓名/节数/费用），并同步把 runner.rs / exec.rs 单测里「手动追加」的部分删掉、改为断言方案自带两个输出。字段名与派生表列名在方案里现成，GUI 输出页也能加。

4. 根因②：XML patch 把数值写进了字符串型单元格

4.1 机理

  1. 引擎的模板回写是「最小 XML patch」：plan_template_patch 算出值后，只把目标单元格 <c> 里 <v> 的文本替换掉（xmlpatch.rs 的 patch_one）。它完全不管单元格的 t（类型）属性，也不管旧值是不是字符串下标。
  2. 你清空绩效表数据时用的表格软件把空单元格存成了 <c r="…" s="…" t="s"/>（字符串型空单元格）。该文件 docProps/app.xml 里 <Application>Tencent office</Application>，即腾讯 Office 保存；对照写回前的 .bak，数据区 J3、K3 等全部是 t="s" 空单元格。
  3. patch 往 <c … t="s"/> 里填 <v>100</v> 后得到 <c r="J3" s="75" t="s"><v>100</v></c>。按 OOXML 规则，t="s" 单元格的 <v> 是共享字符串表下标——Excel / WPS / 腾讯表格打开时把 100 解释为「第 100 项字符串」。而绩效模板的共享字符串表里 0~141 项恰好是表头 + 全校老师姓名。
应写数值写进字符串表下标表格实际显示
100（考勤奖等）#100肖雅静（老师姓名）
50（岗位奖）#50梁建（老师姓名）
40（纯行政岗位奖）#40吴红莲（老师姓名）
30 及更小的整数#3…#30姓名 / 课时S / 考勤奖 等表头文本
0#0空串（看似空白）
小数（198.8 等）或大于 141 的整数非法下标空白 / 异常（取决于客户端宽容度）

对写回的 2423 个单元格做统计：唯一值 421 个，其中 121 个是 1..141 的整数——这些单元格都会被显示成「人名字典」，正是你看到的「乱七八糟的名字」。

4.2 为什么以前（仓库里已提交的 绩效.xlsx）是好的

Git 里已提交的 绩效.xlsx（与 golden 相同）数据区单元格是无 t 属性的纯数值单元格。用这种模板回写时，patch 得到的是正常数值格（第 2 节「干净模板」列已验证）。缺陷是模板依赖的：模板目标列一旦是字符串型空单元格，写回即乱码。

修复动作 B：写回层要按值的类型管理单元格类型——写数值时保证目标 <c> 不带 t="s"（必要时把 t 属性从开标签里剥掉）；清空（空值）时移除 <v>（可顺带清 t，避免残留字符串型空单元格）。并补回归单测：用「数据区全是 t="s" 空单元格」的模板跑一遍，再用 calamine 回读断言是 Data::Int/Float 而不是 Data::String。

5. 为什么校验 / Dry-run 都没拦住

检查点为什么漏过
方案校验（validate）只做静态引用检查：bukesh 派生表被绩效「补课时」字段引用了（bukesh.费用），所以校验通过。校验不检查「某个派生结果该不该落盘成文件」，也不检查模板单元格类型。
Dry-run 预览dry-run 输出列表本来就只有 jx 一项——如果之前点过预览，日志里其实已经能看到「只有 1 个输出」，只是界面没把它当异常提示。
模板读取/定位calamine 把 t="s" 的空单元格读成空值，定位、规划一切正常，读不出「类型危险」。

7. 对现有数据的损害与恢复

重要：绩效.xlsx.bak 不能帮你恢复数值。该 .bak 是引擎在写回前一刻自动备份的「已被你清空的模板」，里面本来就没有数。真正含正确数值的旧文件是 Git 里的版本。
文件现状恢复建议
testdata/2023-09/绩效.xlsx被写坏（字符串乱码）如 2023-09 只是示例数据：git checkout 恢复该文件，恢复版本与 golden 一致、数值正确。若已按真实月数据重算，请以 .bak 为「清理底稿」、修好引擎后再跑一次。
testdata/2023-09/补课时.xlsx已被删除可 git restore 找回旧产物；修好方案输出后再重新生成。
testdata/2023-09/绩效.xlsx.bak清空后模板（引擎自动备份）可作为干净模板底稿供修复后重跑；勿当数据备份。

如果这目录是要交给学校的真实月数据，请优先用你自己那边的原表恢复，别依赖本仓库。

8. 修复建议（待你拍板）

建议 A｜方案补上新文件输出（治 ①）——低风险

在 schemes/高中月绩效复刻.json 的 outputs 数组追加（等价内容也可在 GUI 输出页添加）：

{
  "id": "bks",
  "kind": {
    "new_file": {
      "file": "补课时.xlsx",
      "from": "bukesh",
      "sheet": "替上课补课时",
      "columns": [
        { "header": "姓名", "field": "姓名" },
        { "header": "节数", "field": "节数" },
        { "header": "费用", "field": "费用" }
      ]
    }
  }
}
  • 同步修改 runner.rs、exec.rs 里「手动追加该输出」的单测，改为断言方案自带 2 个输出，并继续与 2023-09-golden/bukeshi/补课时.xlsx 逐人对拍。
  • 写回后目录里会多出补课时.xlsx；是否兼容旧程序两 sheet 形态（Sheet1 + 替上课补课时），见第 9 节遗留风险。

建议 B｜写回层管理单元格类型（治 ②）——核心修复

  1. 让 SheetEdit / 规划结果携带值类型（数值/空），或让 patch_one 增加「按数值写」分支：写入时把开标签里的 t="s"（及其它类型属性）剥掉，产出不带 t 的数值单元格；值为空时移除 v（建议一并剥 t，避免留下字符串型空单元格给下一次运行埋雷）。
  2. 补回归单测（重要）：造一个「数据列全是 t="s" 空单元格」的模板（等价于腾讯 Office 清空后的形态）→ 跑写回 → calamine 回读断言目标格为 Data::Int / Data::Float；再补「清空后单元格不再是字符串型」的断言。
  3. 可选加固：plan_template_patch 打开模板后扫描目标列，若发现目标单元格为 t="s" 形态，给出 warning（「模板目标单元格为文本型空串，将按数值重写类型」）。

建议 C｜运行入口/UI 防呆（可选增强）

  • 实际写回前，日志/对话框明确列出「本方案将产出 N 个文件：绩效.xlsx（回写）、补课时.xlsx（新建）」之类清单；Dry-run 与实跑共用同一清单展示。
  • 写回前对模板做「目标单元格类型」体检，类型可疑时提示或中断（配合建议 B 的 warning）。

9. 遗留风险提示（顺带发现，不在本次故障内）

  1. 补课时新文件的形态差异：旧程序（Go kpi）产出的补课时.xlsx 是 Sheet1 + 替上课补课时 两个 sheet；引擎 writer.rs（rust_xlsxwriter）只会按方案建一个替上课补课时 sheet。若学校流程依赖「第一个 sheet 是 Sheet1」，需要在方案层约定或接受差异。golden 对拍按「姓名→节数/费用」集合比对，掩盖了这一版式差异。
  2. 空单元格插入无样式（M0-0.8 遗留）：xmlpatch.rs 的 insert_new_cell 新建 c 不带同列 s 样式，人员/列缺失时会出现无边框无格式的格子。
  3. 公式缓存：若模板目标格含公式（f 元素），只改 v 不改公式，Excel 打开重算可能覆盖写回值。当前示例模板数据区无公式所以未触发；写回层对 f 的处理值得明确策略（删 f 或拒绝）。
  4. 本次工作区还有两处无关改动（godot/main.tscn、ui/nav.rs 帮助弹窗配色），与本次故障无关，可正常保留。
